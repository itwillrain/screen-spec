# API 連携（apiBindings）

画面がどの API を呼び、画面項目がどの API フィールドに対応するかを記述します。v0.1 は **案B**：
`operationId` / `specRef` で OpenAPI を参照し、**対応関係のみ**を書きます。

- 型・制約は OpenAPI 側を**真実の源**として参照に委ねる（screen-spec 側で再定義しない）
- `apiBindings` はマップ（キーが連携識別子・camelCase）

## 例

```yaml
apiBindings:
  getUser:
    openapi:
      operationId: getUserById
      specRef: ./openapi/users.yaml
    request:
      path:
        userId: "{screen.route.userId}"
    response:
      mapping:
        name: data.name
        email: data.email
  updateUser:
    openapi:
      operationId: updateUserById
      specRef: ./openapi/users.yaml
    request:
      body:
        name: "{fields.name}"
        email: "{fields.email}"
```

イベントからは `action.apiCall` で連携を参照します。

```yaml
events:
  submit:
    from: editing
    to: submitting
    action: { apiCall: updateUser }
    onSuccess: { to: viewing }
    onError: { to: error }
```

## 式（expression）

`request` の値は**テンプレート式**です。リテラル文字列と `{参照}` の並びで表します。

- `{screen.route.userId}` … ルートパラメータ
- `{fields.name}` … 画面項目の値
- `/users/{screen.route.userId}` … リテラル＋補間の混在
- `response.mapping` の値（`data.name` 等）は API レスポンス内のパス

テンプレートはパースされ、参照が検証されます（`fields.X` が実在フィールドか、
`screen.route.Y` が route パラメータか）。構文エラー・未対応の参照ルートは **warning**。
評価（実データの当てはめ）は設計書のスコープ外です。

:::note
`specRef` の OpenAPI 定義は operationId の存在を検証します（型・スキーマの厳密な突合は行いません）。
:::

## ビューアでの連携表示

ビューアの「API 連携」タブは `specRef` を実際に解決し、各バインディングが呼ぶ **operation の
メソッド・パス・パラメータ・リクエスト/レスポンス項目**を表示します。マッピングした項目が
OpenAPI 側に存在しない場合は印（`?`）で示します。

さらに各バインディングから **Redoc / Swagger UI** で OpenAPI を開くリンクを提供します
（Redoc は該当 operation へディープリンク）。外部ツールは spec を URL で取得するため、
**公開URLで配信されている場合**に機能します（ローカル dev では localhost が外部から取得できません）。

## 診断

- `event.action.apiCall` が未定義の `apiBindings` を参照 → **warning**
- 式 `{fields.X}` が未定義フィールドを参照 → **warning**
- 式 `{screen.route.Y}` が route に無いパラメータを参照 → **warning**
- `response.mapping` のキーが未定義フィールド → **warning**
- （複数画面時）`transition.to` / `onSuccess.navigate` が未知の画面 id を参照 → **warning**
