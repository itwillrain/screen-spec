# ADR 0002 — 仕様カバレッジの振り返り（テスト生成・実装の観点）

- ステータス: **Accepted**（ロードマップ）。優先度1（バリデーション形式化）は完了。
- 日付: 2026-07-25

前提: 「画面詳細設計書（screen-spec）をもとに**テスト項目書**を生成し、**実装**の足場にする」。
その観点で現状の到達度と不足を棚卸しする。

## 現状のカバレッジ

画面 / 項目（type・required・validations・options・visibleWhen・width・permission）/
状態遷移（states・events・transitions）/ API 連携（apiBindings＋実 OpenAPI 解決）/
params（path・query）/ layout / design / `$ref` / compose / 式・条件式エンジン。

→ **「何を・どの構造で・どの API と・どの状態遷移で」は SSOT として強い。**

## テスト項目書の生成観点

**導出できる**: 入力バリデーション、状態遷移（from→to・onSuccess/onError）、表示条件（visibleWhen）、
API 呼び出し（送信/反映・成功/失敗）、パラメータ（必須・既定・enum）。

**不足（要形式化）**:
1. **バリデーション意味論が非形式的**（`rule` が自由文字列）→ 境界値・同値分割を自動導出できない。**最重要**。
2. 数値/日付の範囲・桁・step が表現できない。
3. **期待結果（アサーション）が薄い**。event/transition は遷移先のみ。onError も状態のみで、
   HTTP コード別の挙動・エラーメッセージが書けない。
4. ガード条件が無い（案C）→ 条件付き遷移のテストが導けない。
5. 権限マトリクスが緩い（access/editRoles）→ 役割×項目×操作の明示が欲しい。
6. 前提データ/フィクスチャが無い（編集画面＝既存データ存在 等）。
7. フィールド既定値が無い（param の default はあるが field には無い）。
8. 業務ルール/受け入れ条件は本質的に画面仕様の外 → 別ソース（AC）が要る。

## 実装の観点

**できる**: 画面スキャフォールド＋データバインディングの生成。
**足りない**: バリデーション意味論、フィールド既定値・編集可否条件、エラーハンドリング詳細、
表示フォーマット。→ **「動く実装」ではなく「実装の契約・足場」。**

## あえてスコープ外（別レイヤ）

実描画・スタイル・UI フレームワーク依存、i18n、業務ルール/受け入れ条件、ランタイム微挙動。

## ロードマップ（優先度）

1. **バリデーションの形式化**（既知語彙＋型付き値、未知語彙は warning）✅ 完了
2. event/transition の期待結果（`expects`）＋ API エラー→挙動/メッセージのマッピング ✅ 完了
3. 権限マトリクスの明示化（role×field×操作）
4. フィールド既定値・編集可否条件（`enabledWhen`）
5. 前提データ/受け入れ条件の置き場所（screen 内 or 別ドキュメント）を決める
6. （将来）ガード条件（案B 方向・後方互換で追加）

## 結論

SSOT・実装の足場としては強い。テスト自動生成と完全実装には
**① バリデーション意味論 ② 期待結果/エラー挙動 ③ 権限マトリクス**の形式化が鍵。
業務ルール・描画詳細は別ソースと割り切る。
