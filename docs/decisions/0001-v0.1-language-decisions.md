# ADR 0001 — v0.1 言語設計判断

- ステータス: **Accepted**（`v0.1.0` で実装済み）
- 決定日: 2026-07-23（企画・設計フェーズ）／昇格日: 2026-07-24
- 出典: `.knowledge/decisions.md`（検討メモ）を確認のうえ昇格

画面詳細設計書を記述する OpenAPI ライクな言語仕様 v0.1 の、承認済みの設計判断（#1〜#12）を記録する。

## 目的

- 人間と AI の双方が読み書きしやすい、画面詳細設計書の記述言語を作る。
- YAML を主な記述形式とし、JSON Schema で検証できるようにする。
- 特定の UI フレームワークに依存しない。
- 画面・項目・状態・イベント・バリデーション・権限・API 連携・画面遷移を表現できる。
- v0.1 は実画面の自動生成ではなく、**画面詳細設計書の Viewer** を目指す。
- 将来的な拡張と後方互換性を考慮する。

---

## 決定 #1 — 記述形式

**決定**: YAML を主な記述形式とし、JSON Schema (draft 2020-12) で検証する。
**根拠**: 人間・AI 双方が読み書きしやすく、既存の検証エコシステム（ajv）に載る。
**実装**: `schema/screen.schema.json`, `packages/core`（js-yaml + ajv）。

## 決定 #2 — コンポーネント再利用

**決定**: 再利用は `components` セクション + `$ref` で行い、**v0.1 から必須**とする。
**根拠**: OpenAPI の `components`/`$ref` モデルを踏襲し、共通部品の単一情報源を保つ。
**実装**: スキーマの `components`（validations/fields/options）＋リゾルバ。

## 決定 #3 — `$ref` のセマンティクス

**決定**: **純粋参照**。`$ref` を持つオブジェクトに兄弟キーを書けない（マージ・上書き不可、OpenAPI 3.0 互換）。
**根拠**: 単一情報源を崩さず、差分・レビューを追いやすくする。リゾルバが単純化する。
**実装**: スキーマの `oneOf[refObject, def]`＋リゾルバの兄弟キー拒否。
**補足**: screen-spec の `$ref` は「インスタンス（データ）参照」で、JSON Schema の `$ref`（スキーマ参照）とは意味が異なる。

## 決定 #4 — バリエーション

**決定**: 「共通定義＋少し違う版」は上書きではなく**別コンポーネントとして定義**する。
**根拠**: #3（純粋参照）の帰結。単一情報源を保つ。

## 決定 #5 — コレクション構造

**決定**: 配列＋`id` をやめ、**全面マップ化**（キー＝識別子、`id` プロパティ廃止）。
**根拠**: OpenAPI 同様に識別子をキーで表現でき、`$ref` の純粋性も保てる。
**補足**: `screen.id` のようなトップレベル単体の識別子は残す（マップのキーに相当がないため）。廃止はコレクション内の `id` のみ。

## 決定 #6 — 表示順

**決定**: **YAML の記述順を表示順とする**。
**根拠**: マップは構造的に順序非依存だが、`js-yaml` は挿入順を保持するため実務上機能する。厳密なレイアウトは後続で扱う。

## 決定 #7 — 参照解決

**決定**: `core` にリゾルバを持ち、**raw → resolve → resolved の 2 段検証**を行う。
**根拠**: `$ref` はインスタンス参照のため JSON Schema 単体では完結しない。段 1 で生を検証、解決後に段 2 で正規化文書を再検証し、参照先の型ミスマッチを検出する。
**実装**: `packages/core/src/resolve.ts`, `validate.ts`。

## 決定 #8 — 外部参照

**決定**: 外部 `$ref` は**ローカル相対パスのみ**（`http(s)://`・絶対パスは v0.1 非スコープ）。
**根拠**: セキュリティと単純性。作者は相対パスを書き、解決基準（file:// / http(s)://）は実行環境が与える。
**実装**: リゾルバの `isAllowedRelative` チェック。

## 決定 #9 — キー命名規則

**決定**: 識別子を用途別 3 規則に分け、`patternProperties` で機械的に縛る。

| 識別子の種類 | 規則 | 検証パターン |
|---|---|---|
| コンポーネント定義名（`components.*` のキー） | PascalCase | `^[A-Z][A-Za-z0-9]*$` |
| コレクションのキー（`fields`/`states`/`events` 等） | camelCase | `^[a-z][A-Za-z0-9]*$` |
| 画面 ID（`screen.id`） | kebab-case | `^[a-z][a-z0-9]*(-[a-z0-9]+)*$` |

**根拠**: OpenAPI の慣習（定義名 Pascal / ペイロード camel）に倣う。`$ref` パスを見ただけで定義か実体かを区別できる。

## 決定 #10 — 状態遷移の厳密さ（案C）

**決定**: **案C（中間）**。`states` はマップで全状態を定義し 1 つを `initial: true`。`events` は `from`/`to` 必須。未定義状態参照は error、網羅性（到達不能・initial 個数）は warning。
**根拠**: 厳密ステートマシン（案B）は手書き・AI 生成の負担が過大。緩すぎる（案A）と図が描けない。設計書は実装より前に書かれるため書きかけを許容する。
**非スコープ（案B の要素）**: ガード条件式、入れ子/並行状態、履歴状態、遷移の副作用スクリプト。
**後方互換方針**: 案C は案B の下位互換な部分集合として設計。将来の拡張は任意キー追加／オプトインで行い、v0.1 の設計書は書き直し不要。

| B で足す要素 | v0.1(C) での扱い | 後方互換の担保 |
|---|---|---|
| ガード条件 `guard` | 書けない | `event.guard` を任意キー追加 → 既存は無指定＝常に真 |
| 入れ子/並行状態 | フラットのみ | `state.states`（子状態）を任意追加 → 既存はフラットのまま有効 |
| 網羅性の強制 | 到達不能は警告 | `x-strict: true` 等のオプトインでエラー昇格 |

**実装**: スキーマの `states`/`events`/`transitions`、`packages/core/src/analyze.ts`。

## 決定 #11 — OpenAPI 連携の深さ（案B）

**決定**: **案B（参照＋マッピング）**。`apiBindings` はマップで、各バインディングは `openapi: { operationId, specRef }` を必須で持ち、`request`/`response` に**画面項目 ⇔ API フィールドの対応のみ**を記述する。
**根拠**: 型・制約は OpenAPI を真実の源として参照に委ね、二重管理を避ける。設計書の核心は「どの項目がどの API フィールドに対応するか」。
**非スコープ**: 型・バリデーションの再定義（OpenAPI に委譲）、変換ロジック、リトライ/タイムアウト等の実行時ポリシー。式（`{fields.x}` 等）は v0.1 では未パース。`specRef` の OpenAPI 定義も未解決（参照のみ）。
**実装**: スキーマの `apiBindings`、`analyze.ts`（`action.apiCall` の参照検査 = warning）。

## 決定 #12 — `compose`（allOf 相当）

> **Superseded by [ADR 0009](./0009-component-and-screen-data-boundaries.md)**（2026-07-28）。Componentを完全な契約として扱い、`compose`は互換期間を設けず削除する。以下は廃止決定前の記録。

**決定（当初）**: 予約のみ・v0.1 非スコープ。将来「合成の明示宣言」として導入する余地を残す。
**更新（v0.1 系で実装）**: `compose` を実装した。`compose: [entry, ...]` の各要素を順に**深くマージ（後勝ち）**し、
さらに兄弟キー（`compose` 以外）を最優先でマージする。`$ref` 単体の純粋性（#3）は保つ（compose は別キーによる明示宣言）。
マージ結果は本来の型として stage-2 で再検証される。使える位置は Field / Validation。
**根拠**: `$ref` は純粋参照（#3）のため重複が生じうる。別コンポーネント定義（#4）に加え、
上書き系のバリエーションを明示合成で表現できるようにした。
**実装**: `packages/core/src/resolve.ts`（`resolveComposeObject` / `deepMerge`）、スキーマの `composeObject`。

## スコープ / 非スコープ（v0.1）

### スコープ
- Screen を記述する YAML 言語仕様（Field / State / Event / Validation / Permission / ApiBinding / Transition）
- `components` + `$ref` によるコンポーネント再利用（必須）
- JSON Schema (draft 2020-12) + リゾルバによる 2 段検証＋意味解析
- 設計書を閲覧する Viewer（読み取り専用）

### 非スコープ
- 実 UI コードの自動生成
- 大規模な画面遷移図の自動レイアウト（一覧・簡易グラフ止まり）
- 認証・認可の実行時制御（権限は設計情報としてのみ記述）
- 本格的な i18n 管理、リアルタイム共同編集、WYSIWYG エディタ
- `http(s)://` による外部参照、`$ref` の兄弟キーマージ、`compose`

## 実装状況

すべて `v0.1.0`（M1〜M5）で実装済み。CLI（`screen-spec validate`）、ドキュメントサイト（Blume）、
ビューア（Swagger UI 型・複数画面＋画面間遷移可視化）を含む。
